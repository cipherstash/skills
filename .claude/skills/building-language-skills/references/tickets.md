# Ticket breakdown

Split a language's skills into five tickets. Each first slice is a tracer bullet: it runs the whole path for one skill on a narrow scope, so later tickets only widen it. Copy the acceptance criteria from the Go ticket named in each row, and change what is specific to the language. Add each item [gotchas.md](gotchas.md) marks as a criterion for that ticket.

## What each ticket proves

1. **Practices first slice.** Two references: one ported from upstream with its audited defects fixed, and one written new for an area upstream lacks. With no upstream skill, both are written new. The examples module and its script test. The script test runs none of the suite's checks: it matches every quoted block to its source, as CONTRIBUTING.md's **Language skills** section says. Only the examples the spec lists for those two references. The check suite, as the spec drafted it: the `references/checks.md` reference with its pinned-versions table, a CI job in the validate workflow that runs the suite over the examples with the CI toolchain install, and the drift test under `scripts/tests/` that checks each suite check is in place in that job and its version matches the table. Go's are `golang-practices`' `references/checks.md`, the `go-check-suite` job, and `test_go_check_suite_workflow.py`. The drift test reads the table with the shared parser `scripts/tests/language_drift.py`, as CONTRIBUTING.md's **Shared rules for every language** says, and does not write a parser of its own. Subclass `DriftTests`, and set `CHECKS` to the practices skill's `references/checks.md` and `JOB` to the suite's job. Set `LOCKFILES` for each tool pinned through a committed lockfile; the helper knows the frozen install of each lockfile named in its `FROZEN_INSTALLS`, so add any other there first. Add tests only for the language's own checks, as `test_go_check_suite_workflow.py` does. When the skill copies upstream material, add the upstream `LICENSE` and `NOTICE`.
2. **Remaining references.** Every other area in the checklist gets a reference, each quoting the examples module. Build only the examples the spec lists.
3. **Review first slice.** Target resolution, the temporary worktree, the safe-checks reference, the finding contract, and the verdict, applied to two areas. A seeded-defect fixture with one planted defect for each of those two areas, its `expected-findings.md`, and its script test. The review quotes CI's result for each suite check CI ran on the reviewed head commit, since CI is the gate. It fetches only a suite tool that is not installed, at the version the practices skill has pinned, into `.<lang>-review-tools/`, with install scripts off, as **The review skill** in [gotchas.md](gotchas.md) says. Its criteria name each file and flag of the execution surface the spec lists, and say the review runs nothing when the change touches one, until the user says yes.
4. **Remaining areas.** One step reference per remaining area, and one planted fixture defect per area. A Repository standards step compares the repository's CI with the check suite, as `golang-review`'s **The check suite in CI** does for Go. A missing check is a line in the report, not a finding. A weakened check is a `major` finding. A missing untrusted-input test is a `minor` finding, for a function the change adds.
5. **Release ticket.** When an upstream plugin exists, remove it from every catalog that lists it and from the bundled-plugin lists in `scripts/validate.py`. Update the README. When an upstream plugin was removed, add uninstall steps for it modelled on the `golang-pro` note. Run strict plugin validation, the behavior cases on both hosts, and the fixture review by hand. Leave out #62's version bump and its merge to `main`. The main PR, opened after this ticket merges, does both: only the main PR bumps the version, as build step 12 says.

## Writing each ticket

Each ticket has a `## Parent` line and a `## What to build` section saying what a user can do once it merges. Its `## Acceptance criteria` checklist is one a reviewer can check against the PR. The last criterion is that the checks in build step 8 pass. Every ticket says its work merges into `feat/<lang>-skills`.
