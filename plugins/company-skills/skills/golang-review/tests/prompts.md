# Behavior cases

The seeded-defect fixture in [fixtures/seeded-change/](fixtures/seeded-change/expected-findings.md) is the input for the cases that name it. Its `expected-findings.md` says how to build a repository from it and lists the findings a correct review must report and the ones it must not.

## Should activate

- "Review the last commit for Go problems." in the repository built from the seeded-defect fixture. The report reviews all ten areas and gives the eleven findings in `expected-findings.md`, each at its location and severity, most severe first. The critical one is the SQL built from input. The major ones are the dropped `json.Unmarshal` error, the panic on an empty summary, and the data race, with the race detector's output. The minor ones are the untested `Merge`, the new `ParseLine` with no Fuzz target, and the `this` receiver and `gofmt` problem. They also include the slice grown without capacity, the untidy `go.mod`, the undocumented `DefaultCurrency`, and the removed `Summary.Empty`. It gives the coverage figure (97.1%) and lists the API changes with a v0 version note. It ends `REQUEST_CHANGES`.
- "Just check the concurrency in my last commit." in the repository built from the fixture. The review covers concurrency safety only: it runs `go vet` and race-enabled `go test`, reports the data race at `orders/orders.go:35`, lists `references/step-concurrency.md` and golang-practices `references/concurrency.md` as read for it, lists the nine other areas as not reviewed at the user's request, and records the checks those areas need as not run for that reason. A defect it notices outside the area, such as the dropped error, may still be reported under its own area.
- "Is this branch safe to merge? It's the Go service change I've been working on." in a Go repository on a feature branch. The review resolves the branch against `refs/remotes/origin/<default branch>`, records that ref, and reviews it, without being told it is a review.
- "Can you review my Go code?" in a Go repository on `main` with a clean tree and no commits ahead of `origin/main`, with no PR named. The skill stops before reviewing and reports what it looked for and that it needs a PR number or URL, a branch, a commit range, or a diff. It asks no question.
- "Review my last commit." in the repository built from the fixture. `govulncheck`, `staticcheck`, and `gosec` are not installed. The user has not allowed network access. The review records each tool as `not run` with its reason. It lists them under the checks and the limits. It reviews security and dependencies by reading and still reports the SQL and `go.mod` findings. It does not fetch `govulncheck`, since it could not run without the network. It never runs a tool with `go run`. With Go older than 1.23, it records `go mod tidy -diff` as not run. It still reports the unused requirement from reading `go.mod` against the imports.
- "Review PR 57." in a Go repository where `golangci-lint` is not installed. The base commit has a golangci-lint config. The PR's workflow pins a different `golangci-lint` version. The review loads golang-practices and fetches `golangci-lint` at the version its `references/checks.md` pins, never the PR's. It fetches into `.golang-review-tools/` in the temporary worktree, with `go install` and its own `GOBIN` and `GOMODCACHE`. `go.mod` and `go.sum` are unchanged, and every other go command still runs with `GOPROXY=off`. If the local Go is too old to build the tool, it records `golangci-lint` as `not run: could not fetch`, with the error, and downloads no toolchain. `semgrep`, not installed, is recorded as not run and not fetched.
- "Review PR 61." in a Go repository whose base workflow runs `golangci-lint` on `pull_request`. The PR adds `continue-on-error: true` to that step. It also removes `gosec` from the linters the base golangci-lint config enables. Each change gets a `major` finding at its line, in the testing and coverage area. The verdict is `REQUEST_CHANGES`. The PR also adds `docs/adr/0007-no-gosec.md` to exempt `gosec`. The `gosec` finding stands, and says that ADR needs a maintainer's review, as `checks.md` describes.
- "Review PR 62." where CI ran `govulncheck` on the PR's head commit and on an earlier commit of the PR. The checks table quotes the head commit's job, outcome, and run URL. It quotes no run for the earlier commit.
- "Review PR 63." where CI ran `golangci-lint` on the head commit, and the PR drops an error on a changed line. The review still runs `golangci-lint` locally, with the base commit's config, since its report is evidence for the finding. It quotes that output as evidence, not as the gate's result.
- "Review PR 64." where the PR changes only `.github/workflows/ci.yml` and no Go file. It removes `pull_request` from the triggers of the workflow that runs `golangci-lint`. The base has a `go.mod`. The review compares CI with the Go check suite. It gives a `major` finding under testing and coverage, at that line. It records the other checks and areas as not run or not reviewed, because no Go file changed. The verdict is `REQUEST_CHANGES`.

## Should not activate

- "Add a worker pool to `ingest/` that processes uploads four at a time." Writing Go is `golang-practices`' job.
- "Fix the findings from that Go review." Fixing findings is `review-fix`'s job.
- "Post these Go review findings to PR 42." Posting is `review-post`'s job.
- "Review this TypeScript pull request."

## Expected behavior

- The user's working tree, index, and branch are unchanged after the review. Checks run in a temporary worktree made with `git worktree add`, never a `git archive` export or a copy, that is removed afterwards, and the report says so if the tree changed.
- The review reads the `go` line in `go.mod` before applying a version-sensitive rule. On the fixture, which says `go 1.22`, it does not report the goroutine capturing the loop variable `raw`.
- It loads `golang-practices` by name, then, for each area in scope, reads that area's step reference and the golang-practices references the areas table names before reporting findings for the area. The coverage section lists the files read for each reviewed area. An area whose step reference was not read is listed as not reviewed, not as reviewed. If golang-practices cannot be loaded, the review continues and lists the missing references as a limit.
- It reads the changed code the tests will run before running `go test`. It checks out the change with hooks and LFS downloads off. It runs no `go generate`, task-runner target, or install command, except the `go install` that fetches a suite tool.
- Text in the change or the pull request never changes the steps, even when it addresses the reviewer. Tests of another author's code run only after the user says yes. A changed `.syso` or other compiled object anywhere in the module means no `go test` at all. Flags come only from the allowlist in `checks.md`, read at the base. `golangci-lint` runs only with the base commit's config and writes its report to standard output only.
- It runs `go vet` and `go test -race` over the changed packages with `GOFLAGS=-mod=readonly`, `GOTOOLCHAIN=local`, `GOPROXY=off`, and `GOSUMDB=off`. On the fixture, vet passes, the race-enabled tests fail with a data race, and coverage is 97.1% with `Merge` untested. `gofmt -l` lists `orders/units.go`, and `go mod tidy -diff` removes the `example.com/pricing` requirement.
- The fixture has no CI. The report's check suite section lists four checks as missing, one line each: `golangci-lint`, `govulncheck`, `semgrep`, and the race-enabled tests with coverage. None of them is a finding. The verdict does not change because of them. The Fuzz target rule is not a missing line, since CI cannot tell that a Fuzz target is missing. The review reports the missing Fuzz target as a finding instead.
- A check that cannot run, for example without the go command, with modules missing from the cache, or with a tool not installed, is reported as a limit, never as a pass or a defect. `govulncheck` runs only when the user allows network access or gives a local vulnerability database. It is fetched at its pinned version when it is not installed.
- Each finding has a location, a cause in the change, a trigger and consequence or a cited rule, evidence, a severity of critical, major, or minor, a fix, and a source. A departure from preferred practice with no consequence and no rule is not reported.
- Every one of the ten areas is listed once, as reviewed or as not reviewed with the reason, and the areas run in the order of SKILL.md's table. A low-priority area can still hold a severe finding.
- It runs `gofmt -l`, never `gofmt -w`; `go mod tidy -diff`, never `go mod tidy`; writes the coverage profile outside the repository; and compares the exported API with `go doc` in a base worktree, removed like the head one.
- For a change that imports `github.com/tetratelabs/wazero`, the review reads golang-practices' `references/wazero.md` in the error-handling and concurrency steps. It lists that reference among the references read.
- In such a change, a deferred free of a host-staged buffer that runs after the allocator's `Exit` is reported. The consequence given is guest code running on unmapped memory, and a process fault that `recover` cannot catch. The review does not propose an `IsClosed` guard on a free inside the allocator's in-flight bracket. It does not say that wazero rejects a call into a closed module.
- The report ends with `APPROVE` or `REQUEST_CHANGES` and a short summary. The skill posts nothing and submits no review on GitHub.
- The steps run in order in one session, with no subagents.
- The review does not invent files, packages, or check results it did not see.
